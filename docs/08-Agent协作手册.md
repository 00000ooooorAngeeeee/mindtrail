## 1. 你的身份与使命

你是 **思迹 TrailMind** 项目的开发 agent。这是一个 Windows 桌面端产品（Web 前端 + Java 后端 + MySQL），产品本身用于记录 vibecoding 过程。你的使命是：**按照文档集完成指定的里程碑任务，并把过程如实地记录下来**（本产品 dogfooding，记录格式见 [06-过程记录规范](06-过程记录规范.md)）。

## 4. 编码规范

### 4.1 通用

- 代码注释与提交信息**使用中文**（与产品一致）；标识符/类名/变量用英文
- 遵循现有目录结构（04 §3），不新增顶层目录除非文档更新
- 不提交无关文件（`node_modules`、`target`、本地配置、打包产物进 .gitignore）

### 4.2 后端

- Controller 只做参数校验与路由；业务在 Service；数据访问在 Mapper
- 写操作必须走事务（@Transactional）；删除级联在 Service 显式处理（05 §3）
- API 响应统一结构：`{ "code": 0, "data": …, "message": "ok" }`（code=0 成功）
- 时间一律 ISO-8601 字符串（UTC+8 本地时间）

### 4.3 前端

- 组件按 feature 目录组织；共享组件放 `components/`
- 状态统一走 Zustand；不在组件里散落全局状态
- 画布节点/边的数据变更必须走统一 store action（保证撤销/重做与保存一致性）
- 样式用 CSS Modules（或约定方案，M0 定），不写全局样式污染

### 4.4 数据库

- 所有表结构变更必须同步 `schema.sql`（幂等 CREATE TABLE IF NOT EXISTS + ALTER 兼容）
- 不删列（MVP 阶段用 ALTER 演进，保留兼容）

## 5. 提交规范（Conventional Commits）

**本规范是产品的"证据链"，必须严格执行**（产品依赖 commit message 可读）：

```
<type>(<scope>): <中文主题>

<正文（可选，说明做了什么、为什么）>
```

| type     | 用途       |
| -------- | -------- |
| feat     | 新功能      |
| fix      | 修复       |
| docs     | 文档变更     |
| refactor | 重构（行为不变） |
| test     | 测试       |
| chore    | 构建/工具/依赖 |

示例：

```
feat(session): 实现时间线条目追加与类型选择

- 新增 entry 追加接口 POST /sessions/{id}/entries
- 前端快速记录框支持类型下拉与 Enter 提交
- 单条记录 ≤10s 计时验证通过
```

规则：

- 一次提交一个逻辑单元；禁止"改了一堆还加了个 bug 修复"的混杂提交
- 每个里程碑内小步提交（每完成一个验收项即可提交）
- 提交信息是给未来自己和 agent 读的——**主题用动词开头**，正文写"为什么"（如果和实现相关）

## 6. 测试要求

- 后端：Service 层关键逻辑单测（JUnit 5）；至少覆盖：条目 seq 分配、绑定/解绑、搜索查询、导出还原
- 前端：纯函数单测（树布局算法、content_json 序列化/反序列化、导出渲染）
- 每里程碑结束运行 `scripts/verify` 验收冒烟 + 07 文档验收清单
- 新增功能必须补充对应单测，否则视为未完成（DoD）

## 7. 完成定义（DoD）与里程碑验收

见 [07 §2](07-开发路线图与里程碑.md)。核心：

- [ ] 功能实现且通过验收清单
- [ ] 单测覆盖关键逻辑
- [ ] 文档同步（04/05/06 变化）
- [ ] schema 同步
- [ ] 提交符合规范
- [ ] 过程记录已写（见 §8）

## 8. 每次会话的标准流程（强制）

1. **读文档**：按 §2 顺序读（至少 07 + 相关功能章节）
2. **确认范围**：明确本次会话只做一个验收项（或一个验收项的子任务）
3. **开始记录**：如果本产品可用（M3 后），用思迹开启会话并写 `goal` 条目；不可用（M0-M2）则在仓库 `docs/CHANGELOG.md` 或约定的记录文件中按 06 格式记录
4. **开发**：小步实现 → 单测 → 提交（按 §5）
5. **验证**：运行相关验收清单项，能勾选才提交收尾
6. **写 review**：会话结束时写 `review` 条目：完成情况、与文档的偏差、下次建议
7. **更新文档**：任何架构/数据/接口变化，同步 04/05/06；无法自动同步时在 review 里明确指出

## 9. 给人类用户的会话启动提示词模板

复制以下模板开启一次 vibecoding 会话。「本次任务」填 [AGENTS.md](../AGENTS.md)「当前进度」里第一个未勾选的任务（当前为 **v1.1 P1「C2.4 补记时间 / C2.5 插入条目」**（07 §8 Backlog 第三优先；seq 重排））：

```
你是思迹 TrailMind 项目的开发 agent。请先阅读项目根目录的 AGENTS.md 与 docs/08-Agent协作手册.md，
然后按 docs/07-开发路线图与里程碑.md 的里程碑顺序工作。

本次任务：<为 AGENTS.md「当前进度」第一个未勾选项>

要求：
1. 先读相关文档再动手；
2. 小步实现并提交（Conventional Commits，中文）；
3. 关键逻辑补单测；
4. 会话结束时按 docs/06-过程记录规范.md 写 review，并把文档变更同步回 docs/。
5、每次任务完成后更新docs/中需要变更的内容至最新进程。
6、每次任务完成后在对话中列出剩余任务。
7、当需求文档中v1.1部分全部完成后即可提示开发已初步完成。
```

> 若「本次任务」留空，agent 应读取 AGENTS.md「当前进度」的第一个未勾选项作为本次任务。每完成一个任务并勾选后，本节的「当前为」示例任务需同步后移（写入该会话的 review 记录里）。
## 10. 常见陷阱清单（agent 与人类都要看）

1. **不要绕过 schema.sql 直接改库**：开发中手改的表结构与 schema.sql 不一致 = 事故
2. **不要同时改前后端大范围**：一次会话一个验收项，避免大杂烩提交
3. **树布局算法不要引入重型库**：自研 200 行内；效果验收后再考虑升级
4. **JGit 不要读大仓库全量历史**：带 since/until 与 limit 参数
5. **导出格式不要"顺手优化"**：06 §4 是协议，变更必须升 version 并写迁移说明
6. **记录别造假**：`artifact` 绑定 commit 必须真实存在；找不到就写 `note` 说明
7. **删除工作区要确认级联**：service 层按 05 §3 显式处理
