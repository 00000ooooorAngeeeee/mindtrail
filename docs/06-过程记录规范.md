# 06 · 过程记录规范（产品灵魂）

> 版本：v0.3 ｜ 状态：已定稿 ｜ 面向：产品（记录者）、全栈开发、**所有消费本产品记录的 agent**

> **本文档是"思迹"产品的灵魂定义**：它同时是①产品功能需求（记录模块的行为契约）、②记录写作规范（人和 agent 怎么写好一条记录）、③机器可读协议（导出格式如何被解析）。开发与使用本产品的人/agent 都必须先读本文档。

## 1. 设计目标：一条记录，两个读者

每条时间线记录必须同时满足：

- **人读**：像一条清晰的工作日志——"做了什么、为什么、结果如何"，10 秒内可理解
- **agent 读**：机器可从记录中确定性地提取：时间、类型、内容、关联提交、标签，从而重建"项目如何走到今天"的上下文

**铁律：记录是结构化数据，散文只是它的渲染视图。** 产品内存储与导出都以可解析的结构为准。

## 2. 条目类型体系（枚举，不可扩展于 v1）

| 类型 | 名称 | 用途 | 写作要求 |
|---|---|---|---|
| `goal` | 目标 | 本次要做成什么 | 一句话 + 可验证标准（"完成 X，表现为 Y"） |
| `context` | 背景 | 前置信息：现状、约束、相关链接 | 写清"因为…所以…"，引用已有条目/提交 |
| `prompt` | 指令 | 给 AI 的原始 prompt（vibecoding 特有） | **原文粘贴**，标注模型/工具（如"Cursor, Claude"） |
| `action` | 操作 | 执行的具体动作 | 动词开头："初始化 Spring 工程"；含关键参数 |
| `artifact` | 产出 | 产生了什么成果物 | 指向文件/提交/截图路径；一句话说明它的作用 |
| `decision` | 决策 | 关键选择及其理由 | **必须写理由**："选 A 因为 B（放弃 C 因为 D）" |
| `error` | 错误 | 遇到的故障与修复 | 报错原文（摘录）+ 根因 + 修复动作 |
| `test` | 验证 | 验证行为与结果 | "怎么验的 + 结果通过/失败" |
| `review` | 复盘 | 阶段总结、经验教训 | 面向未来的建议："下次应该…" |
| `next` | 下一步 | 后续计划 | 可勾选完成（前端展示为待办样式，P1） |
| `note` | 备注 | 其他（自由补充） | 无强制要求 |

**最小完备集建议**：一个会话至少包含 1 条 `goal`（开头）、若干 `action/artifact/decision`（过程）、1 条 `review`（结尾）。agent 接手项目时优先读这三类。

## 3. 存储结构（与 05 文档一致）

每条记录 = 一行 `entry` 表记录：

```json
{
  "id": 123,
  "sessionId": 7,
  "seq": 12,
  "type": "decision",
  "contentMd": "选择 React Flow 作为画布引擎…",
  "tags": ["技术选型", "前端"],
  "commits": ["3a1f2c9e0b8d7c6a5b4c3d2e1f0a9b8c7d6e5f4"],
  "createdAt": "2025-06-01T09:40:00"
}
```

- `seq`：会话内唯一递增序号，决定时间线顺序（支持未来插入）
- `commits`：绑定提交 hash 数组（经 `entry_commit` 表）
- 正文 `contentMd`：标准 Markdown（GFM），建议 1-15 行，超长拆分为多条

> **联动引用（v1.1 P1）**：条目可引用导图节点（"条目引用节点"），节点也可挂接条目（"节点挂条目"）——关系存 `node_entry` 表（见 05 §3），**不属于条目本身的结构化字段**，因此不进 06 §4/§4A 导出协议（协议字段形态不变）；联动关系由全量备份覆盖（05 §8）。未来若需进入会话导出，字段形态变更必须升 version（06 §4A 规则 1）。

## 4. 导出格式（Markdown，给 agent 读的权威格式）

会话导出 = 一个 `.md` 文件。**所有 agent 解析思迹记录，以此格式为准。**

```markdown
---
format: trailmind-session
version: 1
session:
  title: 从 0 到 1 搭建 TrailMind 骨架
  status: completed
  workspace: TrailMind
  startedAt: "2025-06-01T09:00:00"
  endedAt: "2025-06-01T11:30:00"
  repoPath: "D:/projects/trailmind"
  gitRange: ["a1b2c3d...", "9f8e7d6..."]   # 会话开始/结束 HEAD
entries: 18
---

# 会话：从 0 到 1 搭建 TrailMind 骨架

## [goal] 09:02 · 目标
搭建可运行的前后端骨架，表现为：双击启动、首页可见、前后端连通。

## [action] 09:10 · 操作
初始化 Spring Boot 工程，依赖：web、mybatis-plus、mysql-connector。
> git: `3f2a1b9` （feat: 初始化 spring boot 骨架）

## [artifact] 09:25 · 产出
- 骨架提交 `3f2a1b9`：可运行的后端服务
- 前端 Vite 工程初始化完成

## [decision] 09:40 · 决策
选 React Flow 而非自研 canvas，因为自由画布（拖拽/连线/缩放）开箱即用；放弃 XMind 类库因为其不可定制自由画布。
> 标签：`技术选型` `前端`

## [error] 09:55 · 错误
MySQL 连接失败：`The server time zone value 'ÖÐ¹ú±ê×¼Ê±¼ä' is unrecognized`
根因：MySQL 时区未配置。修复：`jdbcUrl` 追加 `serverTimezone=Asia/Shanghai`。

- [x] 画布拖拽
- [ ] 双模式切换

```

**解析规则（agent 必须遵守）**：

1. YAML frontmatter 中 `format: trailmind-session` 是本格式标识
2. 条目以 `## [type] HH:mm · 类型名` 为分隔符；`type` 必须是 §2 枚举
3. `> git: \`hash\`` 行表示绑定提交；`> 标签：\`a\` \`b\`` 行表示标签；两者为条目级元数据，可同时存在
4. 条目正文为分隔符到下一分隔符之间的全部 Markdown
5. 时间以条目标题中的 `HH:mm` + frontmatter `startedAt` 日期组合还原

> 实现约定：`gitRange` 与 `> git:` 行输出**完整 40 位 hash**（示例中为缩写示意）；hash 必须真实存在（§5 绑定校验）。

## 4A. 会话 JSON 导出格式（v1，机器可读协议）

会话导出另提供 JSON 文件，供工具/agent 直接反序列化。格式标识 `format: "trailmind-session-json"`、`version: 1`，与 Markdown 导出共用同一数据源，两者条目序列逐项对应。

```json
{
  "format": "trailmind-session-json",
  "version": 1,
  "session": {
    "id": 7,
    "title": "从 0 到 1 搭建 TrailMind 骨架",
    "status": "completed",
    "workspaceId": 3,
    "workspace": "TrailMind",
    "repoPath": "D:/projects/trailmind",
    "startHead": "a1b2c3…（完整 40 位）",
    "endHead": "9f8e7d6…（完整 40 位）",
    "summary": "可选总结",
    "startedAt": "2025-06-01T09:00:00",
    "endedAt": "2025-06-01T11:30:00",
    "createdAt": "2025-06-01T09:00:00",
    "updatedAt": "2025-06-01T11:30:00"
  },
  "entries": [
    {
      "id": 11,
      "sessionId": 7,
      "seq": 1,
      "type": "goal",
      "contentMd": "搭建可运行的前后端骨架",
      "tags": ["验收"],
      "commits": [],
      "createdAt": "2025-06-01T09:02:00",
      "updatedAt": "2025-06-01T09:02:00"
    }
  ],
  "entryCount": 1
}
```

**规则**：

1. `format` 必须为 `trailmind-session-json`，`version` 为整数协议版本（变更字段形态必须升 version，与 §4 同属导出协议）
2. `session` 为会话完整字段，`entries` 为按 `seq` 正序的全部条目；`entryCount` 恒等于 `entries.length`
3. 时间为固定到秒的 ISO-8601 本地时间字符串（`yyyy-MM-dd'T'HH:mm:ss`）；可选字段为 `null`
4. `tags`/`commits` 永为数组（无值为 `[]`），不省略；`commits` 输出完整 40 位 hash

## 5. Git 绑定语义

- **绑定的含义**：`entry_commit(entry_id, hash)` 表示"该条目产出的证据是这次提交"
- **提交感知**：会话激活期间每 5s 检测仓库新提交（`since=start_head`），出现即进入"未绑定提交"缓冲，UI 提供一键绑定到当前条目
- **建议提醒配额**：建议卡片（toast）同一会话最多提醒 3 次；忽略后同批提交不再提醒，绑定后不再提醒；配额按会话持久化
- **绑定校验**：绑定的 hash 必须格式合法（40 位十六进制）且在关联仓库真实存在（防伪造证据）；仓库当前不可读时跳过存在性校验（记录不因仓库移动而丢失）
- **边界**：绑定关系只用于**追溯与展示**，不改变 Git 仓库本身；不自动创建提交、不修改历史
- **约定**：一条 commit 建议只绑定到 1 个条目（主产出）；共享提交（如脚手架）可绑定多个
- **对用户的建议**：commit message 写得具体（如 `feat: 初始化 spring boot 骨架`），因为它是记录的"证据链"

## 6. 记录写作规范（人）

1. **写完即记**：每完成一个可验证的小步骤，追加一条 `action`/`artifact`；养成习惯比内容完美重要
2. **决策必写理由**：`decision` 条目缺理由 = 无效记录
3. **错误条目三要素**：报错原文（摘录即可）、根因、修复动作——这是未来最值钱的资产
4. **prompt 原文粘贴**：不要转述 AI 会话，粘贴原始 prompt + 标注工具，便于复现
5. **一条一事**：超过 15 行就拆分；正文用列表而非长段落
6. **善用标签**：`技术选型`/`bug`/`架构`/`ui` 等，复盘时按标签过滤

## 7. 记录写作规范（agent 在思迹的开发中使用）

当 agent 参与思迹（或任何使用思迹的产品）开发并产生过程记录时，除遵守 §6 外，额外遵守：

1. 每次**会话开始**写 `goal`（可验证标准）；**每个里程碑完成**写 `review`
2. 每个**技术决策**写 `decision`（含放弃的备选方案）
3. 每个**失败与修复**写 `error`；每个**提交**至少对应一条 `artifact`（或绑定到已有条目）
4. **commit message 遵循 08 文档的提交规范**（Conventional Commits），保持证据链可读
5. 记录正文用中文（与产品一致），代码片段用 Markdown 代码块

## 8. Agent 消费协议（新 agent 接手时怎么用这份记录）

1. 找到目标会话的导出 Markdown（或直接读产品内时间线）
2. 按 §4 解析规则还原为结构化条目序列
3. 阅读顺序建议：`goal`（先看目标）→ `decision`（再看关键取舍）→ `review`（吸收经验）→ 按需回看 `error`/`action`
4. 结合 `commits` 与仓库代码对照验证（"记录说做了 X，commit 证明做了 X"）
5. 若发现记录与代码矛盾：以代码为准，并在后续 `review` 中修正记录

## 9. 产品内实现要求（开发约束）

| 要求 | 说明 |
|---|---|
| 快速记录 | 底部输入框 + 类型下拉 + Enter 提交，≤10 秒完成（NFR） |
| 类型默认记忆 | 记住上次用的类型 |
| Markdown 渲染 | 条目卡片展开渲染 GFM（代码块/列表/引用/粗斜体）；编辑时 WYSIWYG 编辑器（CodeMirror） |
| 导出一致性 | 导出实现必须通过"解析-还原"往返测试：Markdown 导出 → 按 §4 解析、JSON 导出 → 按 §4A 反序列化 → 与库中数据逐一比对 |
| 时间补记 | **已落地（v1.1 P1，PRD C2.4）**：追加/编辑条目均可指定创建时间（ISO-8601 精确到秒，编辑面板 datetime-local 输入，未改动不覆盖） |
| 插入条目 | **已落地（v1.1 P1，PRD C2.5）**：条目卡片「插入」→ 插入到该条之后（afterSeq，0=最前），其后条目 seq+1 重排 |
