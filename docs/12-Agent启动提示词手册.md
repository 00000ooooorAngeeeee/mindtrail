# 12 · Agent 启动提示词手册（人类使用）

> 版本：v0.1 ｜ 状态：已定稿 ｜ 面向：**人类开发者/维护者**（使用 agent 改进和维护思迹 TrailMind 时的启动指南）
>
> 本文档回答一个问题：**"我要让 agent 帮我做事，提示词该怎么写、要带什么信息，才能让它以最好状态完成？"**
> 与 [08-Agent协作手册](08-Agent协作手册.md) 的关系：08 是给 agent 读的内部工作约定（它做什么、怎么遵守规范）；本文档是给人类读的使用指南（你怎么启动它、怎么把需求讲清楚）。

## 1. 核心原则（先读这 5 条）

1. **一次会话只做一个任务**（08 §8）：不要在一个提示词里塞"修 bug + 加功能 + 重构"；一个任务对应一个会话，最稳。
2. **验收标准必须写进提示词**：agent 以"可勾选的验收清单"为完成定义（07 §2 DoD）。没有验收标准的任务 = 让 agent 猜。
3. **必带三要素**：做什么（任务）→ 期望（验收）→ 约束（不要做什么/遵守什么）。约束尤其重要：`不要改导出协议`、`不要动 schema` 这类"禁止项"能省大量返工。
4. **环境信息一次给全**：项目根目录、数据库凭据位置（.env）、是否已有后端/前端在运行、Electron 是否需要全权限（见 §5）。
5. **过程可追溯**：要求 agent 小步提交（Conventional Commits 中文）+ 按 06 规范在产品内记录过程（dogfooding）。这是本产品灵魂，别省。

## 2. 启动前准备（约 2 分钟）

| 检查项 | 说明 |
|---|---|
| 确认 MySQL 已启动 | 127.0.0.1:3306；根目录 `.env` 含 DB_USER/DB_PASS（gitignore，不提交） |
| 确认仓库干净 | `git status` 无未提交改动再开工（避免 agent 混淆） |
| 确定版本基线 | 读 AGENTS.md「当前进度」：第一个未勾选项即下一个任务 |
| 备好复现信息 | 缺陷任务必带：复现步骤、期望行为、实际行为、截图/日志 |
| 告知运行中服务 | 若后端/前端/Electron 已在跑，告诉 agent 复用或重启（端口 17860/5173） |

## 3. 通用启动模板（所有任务的基础，复制即用）

```text
你是思迹 TrailMind 项目的开发 agent。请先阅读项目根目录的 AGENTS.md 与 docs/08-Agent协作手册.md，
然后按 docs/07-开发路线图与里程碑.md 的里程碑顺序工作。

本次任务：<一句话任务描述>

要求：
1. 先读相关文档再动手（docs/07 → docs/02 → docs/04/05 → docs/06，前端任务加 docs/03；
   维护/接手类任务先读 docs/11-维护与交接手册.md）
2. 小步实现并提交（Conventional Commits，中文主题）
3. 关键逻辑补单测（后端 JUnit / 前端 Vitest / 脚本 node:test）
4. 会话结束时按 docs/06 写 review，并把文档变更同步回 docs/
5. 每次任务完成后更新 docs/ 中需要变更的内容至最新进度
6. 完成后在对话中列出剩余任务

验收标准：
- <逐条可勾选的验收点，见 §4 各场景示例>

约束（禁止项，按需保留/删除）：
- <如：不要改动 docs/06 §4 导出协议；不要新增数据库表；不要改既有 API 契约……>
```

## 4. 场景化模板与验收标准示例

### T1 · 新功能开发（最常见）

在通用模板上：
```text
本次任务：<AGENTS.md「当前进度」第一个未勾选项，或指明 PRD/07 文档中的具体项>

验收标准：
- 功能按 PRD 对应需求实现（引用 docs/02 的条目编号，如 PRD C3.6）
- 关键逻辑有单测；前端 tsc 通过；后端 mvn test 全绿
- scripts/verify.mjs 冒烟 ALL PASS（涉及后端时）
- 文档同步（04/05/06/07 相应变化 + AGENTS.md 进度勾选）
- 过程记录已写入产品（dogfooding，工作区「TrailMind 开发」）
```

### T2 · 缺陷修复

```text
本次任务：修复 bug：<一句话现象>

复现步骤：
1. <步骤 1>
2. <步骤 2>

期望行为：<应当怎样>
实际行为：<实际怎样，附报错原文/截图>

验收标准：
- 按复现步骤回归通过；同类路径无回归
- 根因与修复动作写入 error 类型记录（06 §7.3 三要素：报错/根因/修复）
- 补回归单测（能捕获该 bug 的用例）
```

### T3 · 性能优化

```text
本次任务：优化 <模块> 性能：<现状指标> → 目标 <预算>（参考 docs/04 §8 性能预算）

基线数据：<上次实测值，如 500 节点缩放 194fps>
验收标准：
- 复测脚本（scripts/perf-*.mjs 或新脚本）给出前后对比数据
- 达到或超过预算；无功能性回归（SMOKE 全过）
- 若优化涉及架构性取舍，写 decision 条目记录理由
```

### T4 · 改进建议评估（不确定做不做时）

```text
本次任务：评估改进建议「<建议内容>」并给出结论：值得做吗？怎么做最简？

输出要求：
- 先读相关文档（07 Backlog / 09 风险 / 11 维护手册）判断与现有架构的契合度
- 结论三选一：① 直接做（附最小实现方案与验收标准）② 暂缓（理由与前置条件）③ 不做（理由）
- 若做：按 T1 流程继续；若不做：输出 review 式说明即可，不改代码
```

### T5 · 代码审查 / 架构评审

```text
本次任务：对 <范围：提交区间/模块/整库> 做代码审查。

输出要求：
- 按功能正确性 / 安全与边界 / 性能 / 可维护性 四维列出问题
- 每条标注级别：必须修复 / 建议修改 / 仅供参考
- 不直接改代码（除非用户确认）；可给出修复建议的 diff 思路
- 中文输出；如发现文档与代码矛盾，按 06 §8.5 以代码为准并指出
```

### T6 · 文档维护

```text
本次任务：<更新哪份文档>：<变更内容>

验收标准：
- 与代码现状一致（可对照 docs/11 的代码索引核对）
- 目录/索引同步更新（AGENTS.md 文档索引、08 §2 文档地图）
- 变更点用「<日期> 更新」注释标注（如改动较大）
```

### T7 · 版本发布 / 打包

```text
本次任务：发布版本 <X.Y.Z>（见 docs/11 §5 版本号管理、§6 发布流程）

验收标准：
- 三处版本号同步（backend/pom.xml、desktop/package.json、HealthController；
  注意 desktop/main/index.js 与 electron-builder.yml 的 jar 文件名硬编码）
- npm run build 与 npm run package 成功，安装包位于 release/
- 打包后产物能启动（N4 计时参考 docs/04 §8）
- 版本变更记录写入 CHANGELOG/产品记录
```

### T8 · 数据迁移 / 导出协议变更（高风险，谨慎）

```text
本次任务：<schema 变更 / 导出协议变更>

约束（必带）：
- schema 变更必须同步 docs/05 的 schema.sql（幂等 CREATE TABLE IF NOT EXISTS + ALTER 兼容，不删列）
- 导出协议（docs/06 §4/§4A、05 §8 备份）变更必须升 version 并写迁移说明
- 先写迁移方案（影响面/回滚/数据验证）再动手，方案经我确认后实施

验收标准：
- 旧数据兼容（升级后旧数据可读）
- 迁移脚本幂等可重跑
- 往返测试通过（导出→解析→比对）
```

## 5. Agent 运行环境须知（人类要知道的事）

| 事项 | 说明 |
|---|---|
| **数据库凭据** | agent 从根目录 `.env` 读取 DB_USER/DB_PASS；用 mvn/npm 前它需自行加载 .env（部分场景已内建） |
| **沙箱权限** | agent 默认在受限沙箱运行：esbuild（vitest/vite）、mysql CLI、Electron 等经命名管道的子进程会被 EPERM 拦截；**vitest / verify / Electron 需要你批准全权限执行**（会话中会弹出审批，属正常流程） |
| **Electron 用户数据目录** | 沙箱下 Electron 需 `--user-data-dir` 指向工作区 `.electron-dev/`（已 gitignore），否则 %APPDATA% 只读崩溃 |
| **端口占用** | 17860（后端）/ 5173（前端）。Electron 会接管 17860：探测到本应用残留进程会先杀再拉起 jar；`mvn spring-boot:run` 与 Electron 二选一 |
| **jar 陈旧风险** | Electron 拉起的后端来自 `backend/target/trailmind-backend-0.0.1.jar`——**改了后端代码后必须先 `mvn package` 重建 jar 再启 Electron**，否则跑的是旧代码（本项目真实踩过） |
| **进程区分** | agent 清理残留进程时会按命令行精确区分，不会误杀 DeepSeek Harness 等其它 Electron 应用；但请提醒它注意 |
| **记录约定** | 产品内记录位于工作区「TrailMind 开发」（workspace id 可能变化，agent 按名称查）；GUI 人工目测项按 07 各节标注执行 |

## 6. 交接给下一个人类/agent 时的收尾清单

1. `git status` 干净；所有提交符合 Conventional Commits（中文主题）
2. AGENTS.md「当前进度」已勾选完成项并更新「下一任务」
3. 07 对应验收清单已勾；新增功能有独立小节（任务清单/验收清单/会话切分）
4. 产品内已有该任务的 goal/decision/action/test/error/review 记录（dogfooding）
5. 需要人工做的事（GUI 目测、打包安装验收）已明确列出在会话结论中

## 7. 速查：给 agent 的一句话开场白

- 常规开发：`你是思迹 TrailMind 项目的开发 agent。请先阅读项目根目录的 AGENTS.md 与 docs/08-Agent协作手册.md，然后按 docs/07 的里程碑顺序工作。本次任务：<…>`（08 §9 模板）
- 接手维护：`…先阅读 AGENTS.md、docs/08 与 docs/11-维护与交接手册.md，再处理：<…>`
- 快速问答：`…阅读 AGENTS.md 后回答：<问题>`（agent 会按 fast-path 处理，不写文件）
