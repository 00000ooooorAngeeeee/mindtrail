# 01 · 产品定位与愿景

> 版本：v0.1 ｜ 状态：已评审（PM 单方面） ｜ 更新日期：见 Git 历史

## 1. 一句话定位

**思迹（TrailMind）是一款面向 vibecoder 的 Windows 桌面端工具，把"思维导图"与"开发过程记录"放进同一个工作区，让每一次从 0 到完整产品的 vibecoding 过程，成为给人看、也给 AI 看的结构化资产。**

## 2. 背景与机会

### 2.1 时代背景

AI 辅助编程（vibecoding）已经改变了个体开发者的工作方式：一个人 + 一个 AI agent，可以在数天内完成过去需要团队数周的产品。但随之而来三个新问题：

1. **过程即知识，却在流失**：代码最终会被提交，但"为什么这么设计""试过哪条路失败了""这个 prompt 怎么打磨的"——这些过程信息几乎全部丢失。下次换一个 agent、换一个项目，又从头开始。
2. **给 AI 的"交接班"没有载体**：让新 agent 接手项目时，它只能读代码，读不到决策上下文；而人类记忆同样不可靠。
3. **思考与行动脱节**：画导图用 XMind、写日志用笔记、看提交用 Git 工具——工具割裂，想法与实践无法互相引用。

### 2.2 机会窗口

现有工具各自解决单一问题，但没有一款产品把 **"思考（导图）"与"行动轨迹（vibecoding 过程）"绑定** 并 **以人类+机器双可读的格式沉淀**。这个空白就是思迹的机会。

## 3. 目标用户

### 3.1 主用户画像：vibecoder 小明

- **身份**：个人开发者 / 独立开发者 / 学习者，一人身兼产品、设计、开发
- **场景**：用 Cursor / Claude Code / DeepSeek 等 AI 助手从 0 写一个产品
- **痛点**：
  - 项目做一半，想不起来当初为什么选这个方案
  - 换了新 agent 接手，要花很久重新解释上下文
  - 想复盘"上次的 vibecoding 哪一步最顺畅"，没有数据
  - 想法太多，需要一张图理清结构，但图和工作日志是分离的
- **行为特征**：对工具链有基本动手能力，愿意装 MySQL / 跑本地服务，讨厌数据被云端绑架

### 3.2 次用户：AI agent（未来的读者）

- 思迹的记录**不仅给人读，也给 agent 读**：agent 接手项目时，通过阅读过程时间线快速获得"项目怎么走到今天"的完整上下文
- 因此记录格式必须是 **结构化 + 确定性** 的（见 [06-过程记录规范](06-过程记录规范.md)）

### 3.3 反用户（MVP 不做）

- 团队协作用户（多人实时协作、权限管理）——v1.x 之后再说
- 需要云同步/移动端的用户——本地单机是 MVP 铁律

## 4. 用户故事（核心场景）

| # | 场景 | 用户诉求 |
|---|---|---|
| U1 | 启动新项目 | 建一个"工作区"，里面可以放导图，也可以开过程记录会话，互不干扰又有归属 |
| U2 | 构思阶段 | 用树状导图快速把"这个产品要做什么"展开成一棵结构树 |
| U3 | 自由发散 | 切换到自由画布，随意摆放想法卡片、随手连线，不受树结构约束 |
| U4 | 开工 | 在同一个工作区里开一个"记录会话"，开始 vibecoding |
| U5 | 每完成一步 | 在会话时间线上追加一条记录：目标/操作/产出/决策/下一步，写 Markdown 详情 |
| U6 | 提交代码 | 思迹自动感知到新 commit，把本次提交绑定到当前时间线条目（可选） |
| U7 | 中途走神/换 agent | 让新 agent 读时间线 + 导图，10 分钟理解全部上下文 |
| U8 | 复盘 | 按标签/关键词搜索历史记录，回看"哪类决策最常失败""这个功能怎么一步步做出来的" |
| U9 | 迁移 | 把整个会话导出成一个 Markdown 文件，数据不锁定 |

## 5. 竞品与差异化

| 竞品 | 它解决什么 | 它的空白 |
|---|---|---|
| XMind / MindMaster / 幕布 | 专业的思维导图 | 只画图，不记录过程；格式封闭（导出受限）；不面向 AI |
| Obsidian / Logseq | 本地笔记 + 双向链接 | 没有导图能力（或很弱）；记录靠手动自由书写，无结构化时间线、无 Git 绑定 |
| Cursor / Claude Code / Windsurf | AI 编程本身 | 不做过程沉淀；对话历史与代码产出不形成"项目级资产" |
| Git 客户端 / GitKraken | 提交可视化 | 只有 commit 维度的结果，没有"决策-试错-产出"的过程叙事 |
| DevLog / 开发日志模板 | 写开发日志 | 纯手动模板，无导图、无 Git 自动绑定、无 agent 可读协议 |

**思迹的差异化 = 导图（思考）✕ 时间线（行动）✕ Git 绑定（证据）✕ 双可读格式（人类+AI）**，四者在一个工作区内闭环。

## 6. 价值主张（对用户的收益）

1. **过程可复盘**：vibecoding 完成后，回看时间线就是一部"产品诞生纪录片"
2. **AI 可交接**：换 agent、换电脑、甚至几个月后自己回来，都能快速恢复上下文
3. **思考不丢失**：导图节点与记录会话共存于同一工作区，想法有处安放
4. **数据自己掌控**：本地 MySQL + 可导出 Markdown/JSON，不锁定、不联网

## 7. 产品原则（指导所有决策的北极星）

1. **记录成本必须极低**：任何让记录变麻烦的设计都是缺陷——手动记录 10 秒内完成，其余交给自动化
2. **给 agent 的格式必须严格**：时间线是可解析的数据结构，不是散文（散文只是它的一个视图）
3. **本地优先**：MVP 不依赖任何云服务，断网可用
4. **单机单用户**：不设计账号、权限、协作
5. **导图与记录同等重要**：两者是产品的双翼，缺一不可

## 8. 产品名与定位语

- 产品名：**思迹 TrailMind** ｜ 定位语：*"把思考画成图，把每一步实践写成路标。"*
- 备选：MindTrace / 思径 / MindFlow
- 命名原则：中文名服务中文用户直觉（思=思维导图，迹=过程痕迹），英文名服务可读性（Trail=可追踪的路径）

## 9. 成功指标（如何判断产品做对了）

| 指标 | 目标（产品自用） |
|---|---|
| 会话记录覆盖率 | ≥80% 的 vibecoding 会话被记录（主动+自动） |
| 记录条目均耗时 | 单条手动记录 ≤ 10 秒 |
| 导图创建率 | 每个新工作区至少创建 1 张导图 |
| 回访复用率 | 已完成的会话在 7 天后仍被查看（复盘） |
| 导出使用率 | 会话导出为 Markdown 的功能被实际使用 |

> 这些指标不是商业 KPI，而是判断"产品是否真的好用、真的被使用"的自我检验标准。
